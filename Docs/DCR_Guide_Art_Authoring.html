0. What this guide is, and what it is not

This guide is the standing register of every art slot the game owes, with a generation prompt per slot and two marks per slot: Done (art generated, touched up, imported, wired) and Revisit (wired but earmarked for regeneration). The ledger of record for what is owed stays Docs/ART_DEBT.md, regenerated by Dungeon Core / Audit Art Debt and never hand-edited; this guide is the ledger of prompts and progress on top of it. When the two disagree on what exists, the audit wins -- update this guide to match (chapter 7).

This guide carries no Update-the-Canon chapter, by the same standing instruction that exempts the Content Authoring guide: it records asset production, not design rulings.

Tooling is pixellab.ai for all sprites, with manual touch-up before import. The ComfyUI / dcr_base_generator pipeline described in the Content Authoring guide (chapters 21, 24, 28, 30, 39) is retired; those chapters stand as history and their subject slots are carried forward here where still owed.

1. The Style Contracts (pixellab.ai)

Three contracts. Every prompt is fixed head + subject slot + fixed tail; only the subject slots are listed per item in chapters 2-5. Copy head and tail from here verbatim.

1a. Creature contract (proven in production)

Head: Pixel art style.

Tail: , flat colour fills, clean outline in a darker shade of the subject's own colours, lit from directly overhead, even bright light, no side lighting, no cast shadows, light midtones, bright highlights on the upper surfaces, strong value contrast, no pure black, few colours, minimal shading, no gradients, no dithering, centered, filling most of the frame, full object in view, isolated on a plain solid grey background

Applies to every monster, dwarf, wild beast and NPC body. Stance and facing words live in the subject slot. Most creatures already have N/S/E/W facings and walking animations generated under this contract and awaiting import -- tick Done as they land, use Revisit for the ones that deserve another pass.

1b. Object contract (derived -- validate one before a batch)

Same head and tail as the creature contract. The subject slot leads with the noun and carries a front orthographic view clause in place of any stance wording. Applies to traps, furniture, trophies, crates, and the arrow. Derived from the proven creature contract, not yet proven itself: generate one object, judge it in place, then run the batch.

1c. UI emblem contract (unproven -- validate one on the plank first)

Emblems harmonise with the wooden UI kit -- the plank every themed button uses is Assets/Art/UI_Elements/_IN_USE/TEXT BTN empty.png (dark rounded outline, warm wood, soft top sheen). Emblems sit on that plank and its boards, so they match its palette and outline language rather than the chunky world-sprite look.

Head: Game UI icon, painted style.

Tail: , single bold centred motif, warm lamplit palette of aged wood, brass and ember tones, one dark rounded outline, soft sheen across the upper edge, simple silhouette readable at small size, no text, no background scene, isolated on a plain solid grey background

Applies to Spell, Tech Node and Pattern icons. This contract has generated nothing yet: produce one emblem, drop it onto the plank in the CAST row or research tree, judge, adjust the tail here if needed, and only then run the batch of 83.

1d. Touch-up checklist (once, here -- not repeated per item)

Between generation and import: outline unbroken and in the subject's own darker shade; baseline level (walkers bob, carts and props must sit flat); stray semi-transparent pixels cleared from the grey key; grey background removed cleanly; silhouette still reads at target size.

1e. Import conventions

PPU 32, filter Point, compression None, Sprite Mode Multiple for animation sets, Single for one-offs. Existing art is inconsistent (owlbear at 32, monster4 at 36, base characters at 16); everything new standardises on 32. Every item in chapters 2, 3 and 5 carries its own target WxH (class tag) line -- the bestiary guide's convention, carried over: the target is the subject's footprint inside a 64 px working frame. The class tag is the body-plan word for the generation template (humanoid, quadruped, winged, coiled, construct, amorphous, and qualifiers). Canvas note: colossal-tagged sprites (Bone Colossus, Behemoth, Leviathan, Storm Roc) read better generated for a 128 downscale -- or keep 64 and accept chunkier giants. Projectiles use a 32 px frame. Emblems are uniform: authored at 128 px square, motif filling ~112, verified for readability at 32.

pixellab.ai exports per-frame PNGs. Landing convention: Assets/Art/Monsters/PixelLab/<MonsterName>/ -- provisional, may shift once bulk import starts; if it does, update this line, nothing else in the guide depends on it.

1f. Wiring rules that outlive any one batch

One sprite, two slots: a monster's south-facing stand frame is its MonsterDefinition.icon; the full facing set is its prefab body. Never author separate portrait art. The same rule collapses each trap to one object sprite serving TrapDefinition.icon and the prefab body.

projectileTint multiplies the sprite: when a bespoke projectile lands, set the definition's tint back to white or the art ships double-coloured. The generators stamp tints fresh-only, so the whitening survives reruns.

Right-facing projectiles: DungeonProjectile rotates right-facing art along the flight heading. The arrow points right or it flies sideways.

2d. The deep occupants (6) -- drifted derivations

Canon 42's nameless things: what a sealed, failed core goes on making with nobody left to shape it. These are not invented from nothing and they are not existing creatures recoloured. Each one is a shipped creature subject pushed until it is recognisable but clearly wrong, because that near-recognition is the horror -- a core makes monsters, so a dead core makes almost monsters.

Why not simply tint an existing body, which was tried first. SpriteRenderer.color is a multiply, so it scales every channel and preserves internal contrast. A high-contrast sprite stays high-contrast, only dimmer -- a skeletal body remains fully legible even at the Pattern Codex silhouette value of 0.06. Darkening cannot produce a silhouette. DamageFlash already records the same finding in its own header: a true silhouette needs a material, not a colour. The drift therefore has to be authored into the shape, which is what this chapter is.

Derived tail -- use this instead of the creature tail in 1a. Only the lighting and value language changes; every structural clause is untouched, so the grey key, the outline rule and every import convention in 1e still apply. The creature tail asks for even bright light, light midtones, bright highlights, strong value contrast, no pure black, which is precisely what keeps a darkened body legible.

, flat colour fills, clean outline in a darker shade of the subject's own colours, lit from directly overhead, dim even light, no side lighting, no cast shadows, low midtones, no bright highlights, narrow value range, deep shadow, muted desaturated palette, few colours, minimal shading, no gradients, no dithering, centered, filling most of the frame, full object in view, isolated on a plain solid grey background

The four drift rules, so a seventh body can be derived without re-deciding.

  1. Keep the mass and the stance. That is the silhouette, and the silhouette carries the recognition. Change it and the body is merely a new monster.
  2. Strip everything implying intent or craft. No club, no sceptre, no regalia, no iron sutures. Canon 42: everything else in the game wants something, and these do not -- that absence is the characterisation. An empty-handed Grave Tyrant is far more wrong than a differently-armed one. This rule does the most work of the four.
  3. Remove the face. Faces are nameable.
  4. Break the count or the finish -- BY REMOVAL, not by addition. A limb missing or unformed, a wing fused shut, smooth surfacing where detail belongs. Subtractive drift is what the model does well at CFG 1; additive drift asks it to BUILD a deformity and fights you. The Chimera Spawn derivation was dropped for exactly this reason -- "a second shoulder where a head should be" is an instruction to construct something, and it could not be got right without pulling in deformations nobody wanted. When picking a seventh donor, pick one whose drift is things TAKEN AWAY.

VALIDATE ONE BEFORE THE BATCH, as 1b and 1c both require. Generate the Behemoth derivation alone, import it, put it on floor index 4 and judge it. The open question is whether the derived tail holds against the subject at CFG 1 -- if it does not, that is one wasted generation rather than six. The negative prompt is inert at CFG 1 and must not be used to fix it; adjust the tail here instead.

7. Updating this guide

The protocol a future chat follows when new art debt appears:

  1. Rerun the audit (Dungeon Core / Audit Art Debt) and push, so Docs/ART_DEBT.md reflects the live tree.
  2. Diff the ledger's REQUIRED and DEFERRED sections against this guide's items. The build-time parity assertions in the original generator did this mechanically; a maintaining chat does it with two greps and a set difference, never by memory.
  3. Add every new slot to the matching chapter with an authored subject slot under the right contract. If the chat cannot author a good prompt (unfamiliar subject, unresolved design), it adds the item with the marker PROMPT NEEDED rather than guessing -- a visible gap beats a wrong prompt.
  4. Never delete an item. A slot that leaves the ledger (asset removed, reclassified by design) gets its heading struck through with a one-line reason, in place -- same convention as canon.
  5. Checkbox ids are stable: dcr-art-v1-<slug-of-asset-name>-d/-r. New items mint new slugs; existing ids never change, so ticked state survives every update. Bump the version prefix only if id meaning changes, which nothing here should ever require.
  6. Edits ride a delivery script against this file with count == 1 anchors, like any guide.

New asset types (a new definition class with a sprite field) additionally need a ruling row in Assets/Editor/ArtDebtAuditor.cs first -- an UNCLASSIFIED line in the ledger means that table needs the entry, and this guide takes the item only once the ledger classifies it.

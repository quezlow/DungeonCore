0. The Pattern, the Rules, the Map

Nearly every content type follows the same four beats: Definition asset (stats and identity) → Prefab (visuals and behaviour components) → Registry (makes it placeable and save-restorable) → Scene/prefab wiring (only where a component holds a direct slot). When a recipe below skips a beat, that is deliberate.

Golden rules

1. Names and IDs are save keys and immutable after ship. DungeonSaveController restores placed content via GetByName: monsterName, roomName, trapName, furnitureName, chestName must never be renamed once a save can contain them. Same for questID and item ID ints. Asset filenames are free.

2. Registry membership = placeable + restorable. If the player can place it and save it, it must be registered. Transient-only definitions stay out -- the Ravenous Bear spawns from WildMonsterEvent's own predatorDef slot and is correctly unregistered.

3. Registry order is presentation only. Lookups are name-based; list order just sets the picker cycle / button order. Reorder freely.

4. Enums persist as ints. AdventurerType and CombatClass are saved as ordinals: append new values at the end, never reorder or remove.

5. One asset per type in adventurerTypes. Def() returns the first match; variants live only in dedicated slots (see the GuardDef incident, canon §2).

2. Wild Monsters (Unified Model)
One definition serves both roles: the floor's wild pool spawns it as an invader, and the registry lists it in the build picker locked behind "Slay one in the wild to learn it". Killing it wild calls BestiaryState.Discover(monsterName) on its own name, which unlocks the same def for placement. No paired assets, no name collisions.
Event beasts are the exception: a wild boss like the Ravenous Bear is wired straight into WildMonsterEvent.predatorDef on its scene object in Dungeon_Level_0 -- transient, never placeable, never registered.
Backlog wording note: the discovery lock line always says "wild" even for adventurer-sourced unlocks (Thrall). Cosmetic; on the passive backlog.

Tuning an existing type

Never add a second asset with the same type to the spawner list -- Def() takes the first match. Variant assets (GuardDef) go only in their dedicated slot (guardDef, used for Noble bodyguards and Inspector escorts).

A whole new type (code required -- touch points only)

Ordinals persist in saves: append-only. Canon §2 holds the intent/goal/faction table.

Combat classes

Adventurer loot

Escort bonus: Mercenary members in an Escort formation (Noble bodyguards) multiply the rolled value by escortGuardLootMultiplier -- that is the whole "guards drop higher-value gear" mechanic; there is no separate guard table.

Owner semantics for reference: a LootTable with owner Adventurer spawns DroppedLoot (core absorbs), owner Monster spawns CarriableLoot (adventurers can steal it). Adventurers also drop whatever they were carrying when killed -- stolen loot and looted gold return to the floor. That is recovery, not authoring. Vestigial: the LootTable component on the shared Adventurer.prefab is cached but never rolled -- per-type adventurer loot has no authoring surface today; differentiation is per-class only.

Names -- all Inspector, no code

Title screen is separate: TitleEncounterDirector in TitleScreen.unity keeps its own adventurerTypes list for the vignette. Monsters flow to the title automatically via the registry; a new adventurer type appears there only if you add its asset to that list too.
4. Items
Items are prefab variants, not ScriptableObjects. The hybrid base prefab carries both UI (Image) and world (SpriteRenderer + CircleCollider2D) faces plus the Item component. The dictionary hardening made the serialised ID the single source of truth: duplicates, zeros, and nulls LogError at Awake.
Footgun: the base Item.prefab is itself live content -- ID 1, "Health Potion". Never repurpose it; always override ID + Name + both sprites on variants. IDs are forever: inventory and hotbar saves store raw ints, quest objectives and rewards reference them. Never reuse a retired ID.

Consumers: InventoryController/HotbarController (save by ID), RewardsController (quest rewards spawn by ID), world pickup via PlayerItemCollector trigger + Item. Batch alternative: the Dungeon Core → Generate Tutorial Content menu appends ItemSpec entries and normalises IDs -- but it also regenerates tutorial quests and dialogue, so prefer manual for one-offs.

7. Traps

A new behaviour is code: append the TrapBehaviour enum, write the TrapBase subclass, add its EnsureBehaviour case, and give the generator a spec. Fifteen behaviours exist as of the trapworks arc. Ambient facts: traps hold fire entirely while global stance is Defensive (TrapsArmed); damage routes through ScaledDamage (Forge census x Trapwright), affliction durations through ScaledDuration.

Picker routing: the trap picker lists registry traps first, then every registered chest with isTrapChest. Treasure chests route to the chest picker instead. The carousel hides affinity-mismatched and unresearched traps -- the tree is the discovery surface, the picker is the toolbox.

10. Quests
Spec path: tutorial-era quests are owned by QuestSpec entries in Assets/Editor/TutorialContentGenerator.cs with the same create-or-overwrite semantics as dialogue -- see the ownership rule in Chapter 11. Edit the spec and re-run; never hand-edit a generated quest asset.
11. NPC Dialogue
Parallel-array gotcha: autoProgressLines and endDialogueLines are bool arrays indexed against dialogueLines -- keep all three the same length. Same inside each DialogueChoice: choices, nextDialogueIndexes, givesQuest run in lockstep, anchored at dialogueIndex.

The spec path: TutorialContentGenerator

The tutorial-town dialogue was not hand-built -- it is generated. Assets/Editor/TutorialContentGenerator.cs holds a DialogueSpec[] array; Dungeon Core → Generate Tutorial Content creates-or-loads each asset in Assets/NPC/Tutorial and stamps every field from its spec.

Ownership rule: a generated asset belongs to its spec -- hand edits in the Inspector are overwritten on the next run. Batch or tutorial content: edit the spec, re-run the menu. One-off NPCs elsewhere: hand-author per the steps above and keep the asset out of the spec list.
12. Odds & Ends

Stairs: one Dungeon/Stairs Definition asset (name, prefab, mana, icon, up-variant sprite) in the DungeonBuildController scene object's slot. Editing the asset is the recipe; there is no registry.

Known stale, deliberately unfixed: the MonsterDefinition header still says "assign to the MonsterSpawner's available types list" (registry is truth); the AdventurerDefinition header still calls itself a combat-class archetype; the AdventurerType enum header says nine types (there are eleven -- canon §2). Trust canon and this guide over header comments.

Importing new art: copy import settings from a sibling sprite in the same folder -- point filter, no compression, pixels-per-unit matched to the sheet (Time Fantasy sheets vary; the character sample imports at 16 PPU, the terrain grid is 32px). A mismatched PPU is the usual cause of a sprite rendering at the wrong scale.

Deliberately out of scope (feature code, not content): new hotkeys (everything routes through the rebindable Keybinds/GameAction system), alert-log strings (feature code; write them in the wisp voice), camera/Cinemachine, save-schema changes (additive-only rule), and scene dressing beyond the generators listed in Chapter 14.

Not covered here: wall sprite assignment (CaveWallSheetLayout -- Wall Sprite Layout guide) and animation controllers (their own guide). Terrain tiles moved to Chapter 15.

13. Audio: Sound Effects
SoundEffectLibrary on the GameController prefab holds SoundEffectGroup entries -- a name plus a list of AudioClips. Code fires them by name via SoundEffectManager.Play("name", randomPitch), picking randomly within the group.

21. Projectile Bolts & Archer Sprites (Ranged Combat)
Ranged combat v1 ships with a runtime-generated soft-glow bolt tinted per definition, and archer bodies borrowed from donor prefabs -- nothing blocks play. This chapter is the road to bespoke art. All prompts follow Guide 1's Style Contract: prefix the fixed head, suffix the fixed tail; only the subject slots live here. Wiring rule to internalise first: projectileTint multiplies the sprite, so pre-coloured bespoke art wants the tint set back to white on that definition. 22. Trapworks Sprites (the nine new traps)
The nine trapworks prefabs ship as stand-ins: the donor spike sprite under an affinity tint, applied by TrapContentGenerator. This chapter is the sprite pass. All are objects/props under the Guide 1 Style Contract: keep the fixed head and tail, drop the tall-proportions clause (creatures only), and lead with the orthographic angle clause immediately after the subject noun. 23. Memory Echoes (the core's own past)
An echo is one wisp line, fired once ever, at a dungeon moment that rhymes with something the player actually did during the living prologue. Canon 34. Three pieces per echo and no more: a line, a table row, a call site. There is no asset, no registry and no save field -- echo lines are authored once = true, so the shipped wispSpokenLines save data already remembers them.

The recipe

Choose the site, not the symptom. The Light echo anchors on the adventurer death path rather than DroppedLoot.Absorb, because the tribute coin flourish runs that same absorb and would fire a memory about stripping the dead when someone left you a gift. Ask what else reaches the line you picked.
Keep them rare. Seven ship, one per affinity plus the old faith, and most players will hear two or three across a whole run. An echo that fires often is not a memory, it is a catchphrase. If a candidate moment happens weekly, it is the wrong moment.

24. The Town's Descendants & the Resting Place
Canon 34. Two pieces of authorable content: the house table that decides which surnames come down out of the prologue town, and the one sprite the resting place wants. Neither has an asset or a registry -- both are code tables, edited in place.

Houses and given names

Surnames must not collide. TryHouseOf matches the last word of a display name, and it is what fires the fall lines. A house sharing a surname with anything in NobleNames.houseNames would make a slain noble speak a descendant's eulogy. The eight shipped surnames are clear of that list; check any new one against it.

The remains sprite

Do not give it a reward. The resting place is the one discovery in the dungeon that pays nothing, and HandleMined deliberately returns early rather than falling through to the entry 17 grant. If a future pass wants to hang something off it, that is a canon change, not a tuning change.
25. Deep Roads (the road profile & its tiles)
Canon 19. The whole road layer is authored through ONE RoadNetworkProfile asset plus one tile. Roads are generated content, not placeable content, so none of the five save registries are involved and there are no permanent ids to protect -- but the profile decides which floors have roads at all, so an empty list means no roads anywhere.
